# Решения и проверяемые границы

## Двойная запись и транзакции

`one_active_booking_per_slot` — частичный уникальный индекс `bookings(starts_at) WHERE status='confirmed'`. Даже обход бизнес-логики не позволяет вставить вторую активную запись на тот же час. Все услуги равны 60 минутам и начинаются в целый час; проверка сетки есть и в схеме. При добавлении произвольной длительности эта модель потребует изменения.

`Database.transaction()` открывает отдельное соединение, выполняет `BEGIN IMMEDIATE`, затем commit или rollback. Никакой блокировки в памяти процесса нет. SQLite WAL позволяет читать при записи; запись последовательно проходит через БД. Ожидание блокировки ограничено 10 секундами, недоступная база даёт HTTP 503. Конфликт уникального слота преобразуется в 409 `slot_taken`.

Перенос — `UPDATE starts_at` внутри той же транзакции. Если новый слот занят, операция откатывается; старое время и ID сохраняются. Не выполняются «отмена старой + отдельное создание новой».

## Повторы и состояния

В `idempotency` уникальна пара `(user_id, request_key)`. Отпечаток учитывает действие, ID записи, услугу и время в UTC. Повтор с другим содержимым получает `idempotency_conflict`. Успешный ответ сохраняется в той же транзакции, что запись и событие. Ошибочные операции не закрепляют ключ.

Повтор возвращает **исходный снимок ответа**, даже если запись затем отменили. Текущее состояние берётся отдельным GET. Новый осознанный запрос должен иметь новый ключ. Веб-интерфейс сохраняет ключ при сетевой ошибке и удаляет после полученного успешного ответа; после перезагрузки страницы эта память не сохраняется. Ограничение БД продолжает защищать слот.

Состояния: `confirmed → cancelled`. Перенос меняет время, сохраняя `confirmed`. Повторная отмена возвращает `cancelled`, не создавая новое событие. Перенос отменённой записи запрещён. Новая запись на освобождённый слот разрешена. Время старта уже наступившей встречи блокирует перенос и первую отмену. CHECK-ограничение связывает статус с `cancelled_at`.

## Идентичность и доступ

Сервер создаёт 256-битный случайный токен. В SQLite хранится только SHA-256. Клиентская cookie — HttpOnly, SameSite=Strict, Path=/api; административная cookie отдельная. HTTPS-флаг настраивается. Клиент не выбирает user_id и не передаёт telegram_id. Чужая и неизвестная запись отвечают одинаковым 404.

Изменяющие запросы требуют специального заголовка. CORS не разрешён: чужой сайт не может сделать такой браузерный запрос с cookie. TrustedHost ограничивает Host локальными адресами. CSP запрещает сторонние скрипты и встраивание. Бизнес-логика доверяет `Principal`, полученному адаптером; её нельзя напрямую выставить через JSON API.

Администратор входит по случайному локальному ключу на 24 часа. В браузере создаётся отдельная сессия. Выход отзывает её; исходный локальный ключ действует до истечения срока. CLI умеет выпускать дополнительный ключ, но интерфейс управления отзывом всех сессий пока отсутствует. Данные сессий и ключи не попадают в Git.

Гостевой доступ подходит для локальной проверки, а не для реального кабинета клиента. Нет rate limiting, восстановления, антиспам-механизма и сложных ролей. До реального размещения эту модель нужно пересмотреть.

## Telegram

Адаптер принимает update только из отдельного polling-процесса, получившего его через HTTPS Bot API. Для команды проверяется личный чат и совпадение отправителя с chat ID. user_id выводится из bot_id и Telegram ID, хешируется; имена и телефоны не сохраняются. Telegram-личность и гостевая веб-сессия различаются.

Изменение записи и сохранение обработанного update происходят в одной SQLite-транзакции. Повтор update возвращает сохранённый текст. Другое содержимое или отправитель с тем же update_id — конфликт. Polling сохраняет offset после отправки ответа. При сбое между отправкой и сохранением offset возможна повторная отправка подтверждения; бизнес-эффект остаётся идемпотентным. Очередь гарантированной доставки не реализована.

## Время и хранение

БД хранит UTC epoch seconds. На границе API требуется timezone-aware ISO 8601. Правила расписания и дни рассчитываются через `ZoneInfo('Europe/Moscow')`, независимо от часового пояса ОС. Веб использует `Intl.DateTimeFormat` с тем же явным часовым поясом. Сессия хранится 30 дней; административный ключ — один день. Записи, события и ключи идемпотентности автоматически не удаляются.

Версия схемы — `PRAGMA user_version=1`; неизвестная версия отклоняется. Миграции следующих версий ещё не требовались и не реализованы. Файловые соединения закрываются после каждой операции. Данные переживают повторный запуск процесса; сброс доступен отдельной ограниченной командой.

## Проверки

`tests/test_service.py`: настоящая SQLite, валидность времени, состояния, ограничения, идемпотентность, доступ и перезапуск. Конкурентные тесты используют восемь потоков, барьер одновременного старта и **независимые соединения к одному файлу**. Один слот: один победитель и семь конфликтов; один повторный запрос: одна запись и семь replay-ответов.

`tests/test_api.py`: настоящие HTTP-маршруты через TestClient и SQLite, cookies, авторизация администратора, CSRF, Host, валидация, безопасные логи и основной цикл записи. Это in-process интеграционные проверки, не внешний HTTP-деплой.

`tests/test_telegram.py`: команды, повторная доставка, конфликт update, чужая запись и личные чаты. Сеть Telegram не используется; реальные сообщения не проверялись.

`tests/test_cli_safety.py`: сброс отказывается трогать другой файл и базу без маркера; услуги сохраняются.

`scripts/browser_check.py`: настоящий локальный HTTP-сервер и Chromium; запись, перенос, отмена, административный вход, сохранение после рестарта; размеры 390, 768, 1440. Реальная SQLite в отдельной временной папке. Снимки делаются из запущенного приложения.

CI выполняет lint, форматирование, mypy и pytest на Python 3.12 / 3.14; отдельная задача запускает Chromium. Сборки frontend нет: сервер отдаёт статические файлы. `permissions: contents: read`; деплой и периодический запуск не настроены.
